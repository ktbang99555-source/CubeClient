# Sub-project B4: 지형 미니맵 — 설계

## 목표

M키로 켜고 끄는 원형 미니맵을 추가한다. 화면 오른쪽 위쪽 어딘가(기존 HUD 편집기로 위치·크기 조절 가능)에 플레이어를 중심으로 실제 블록 색으로 채색된 지형을 북쪽 고정으로 그리고, 그 위에 근처 엔티티를 점으로 겹쳐 표시한다.

레이더형(화살표+점만)이 아니라 실제 지형 색을 그리는 방식으로 확정됐다 — 브레인스토밍 중 시각 companion으로 두 방식을 비교한 뒤 사용자가 직접 선택.

## 범위 밖 (B4에서 안 하는 것)

- **죽은 위치 표시** — 원래 B4에 같이 묶을 계획이었으나, 지형 렌더링 미니맵 자체가 이 프로젝트에서 지금까지 만든 어떤 기능보다 큰 작업이라 사용자와 합의하여 별도 서브프로젝트(B5)로 분리했다. 서버 리스트는 B6로 번호가 밀린다.
- **줌 레벨 조절** — 반경 고정(96블록), 확대/축소 UI 없음. 패널 화면 크기 자체는 기존 리사이즈 핸들로 조절 가능하지만 이건 "같은 반경을 크게/작게 그리는" 것이지 보이는 범위 자체가 달라지는 게 아니다.
- **지도 클릭으로 좌표 이동, 웨이포인트 추가, 다른 플레이어 이름표 표시** 등 확장 기능 — 전부 YAGNI, 필요해지면 나중에 별도로.
- **동굴(지하) 레이어** — 지표면 최상단 블록만 그린다. 바닐라 지도 아이템과 동일한 동작.
- **아직 로드 안 된 청크를 강제로 불러오는 것** — 클라이언트가 이미 로드해둔 범위만 사용, 안 가본 곳은 빈 칸.

## 아키텍처

### `TerrainMinimap`

```
PositionedHudFeature 구현, Category.WORLD
```

- 기존 `PositionedHudFeature`/`HudEditorScreen` 프레임워크를 그대로 재사용 — 드래그 이동, 모서리 리사이즈, 위치 초기화 버튼이 다른 HUD 요소와 동일하게 동작한다.
- 이 모드 두 번째 커스텀 키바인딩(첫 번째는 B3의 Zoom C키). `KeyBindingHelper.registerKeyBinding(KeyBinding)`으로 M키에 등록 — 바닐라 기본 키와 충돌하는지는(B3에서 C키가 `key.saveToolbarActivator`와 충돌했던 것과 같은 함정) 계획 작성 단계에서 반드시 확인한다.
- 켜져 있는 동안만 청크 색상 샘플링·렌더링을 수행 — `CachedConfig` 자가확인 패턴(`ToggleSprint`/`ZoomKey`와 동일).

### 청크 색상 샘플러

- 플레이어를 중심으로 반경 96블록(3×3청크 남짓)에 걸친 청크들을 대상으로 한다.
- 각 청크에 대해 16×16칸을 훑어, 칸마다 지표면 최상단 블록을 찾고 그 블록의 지도 색상을 얻어 청크 하나당 작은 텍스처(`NativeImageBackedTexture`)를 만든다. 최상단 블록 조회와 지도 색상 변환에 쓸 정확한 메서드(`World.getTopY(Heightmap.Type, int, int)`류, `BlockState.getMapColor(...)`류로 추정 — 바닐라 지도 아이템이 쓰는 것과 같은 경로일 것으로 보임)는 **아직 `javap`로 검증되지 않았다**. 계획 작성 단계에서 실제 jar를 뜯어 정확한 시그니처를 확인하고, 안 맞으면 이 절을 갱신한다.
- 텍스처는 청크별로 캐시하고, **매 틱 최대 1개 청크만** 새로 만들거나 갱신한다 — B1에서 "매 프레임 무거운 작업이 FPS를 깎는다"를 겪은 교훈을 여기 그대로 적용. 캐시가 다 찰 때까지는 일부 청크가 며칠 전 미니맵마냥 빈 칸으로 보일 수 있는데, 정상 동작이다.
- 클라이언트가 로드하지 않은 청크는 시도하지 않는다.

### 렌더링 (원형 처리)

- 위 청크 텍스처들을 정사각형 영역에 이어붙여 지형 이미지를 만든 뒤, 고정된 원형 마스크를 씌워 최종적으로 원만 보이게 한다. HUD가 3D 게임 화면 위에 그려지는 구조라 "배경색으로 모서리를 덮는" 방식은 못 쓰고, 실제 알파(투명도)를 깎아내는 방식이 필요하다 — 정확한 GL 기법(스텐실 버퍼 vs 오프스크린 프레임버퍼 합성, 둘 다 공개 `RenderSystem`/`Framebuffer` API 범위 안이라 믹신은 필요 없을 것으로 보임)은 계획 단계에서 확정한다.
- 회전은 북쪽 고정 — 지형 타일은 항상 같은 방향, 플레이어 위치를 나타내는 화살표만 실제 바라보는 방향으로 돈다.
- 리사이즈 핸들은 원이 아니라 그 원을 감싸는 사각형 경계 기준으로 동작한다(기존 `HudEditorScreen.boundsOf()`와 호환).

### 엔티티 점

- 지형과 같은 반경(96블록) 안의 엔티티만 대상.
- 분류: 적대 몹(`Monster` 계열로 추정, 검증 필요) = 빨강, 그 외 우호 몹/동물 = 초록, 다른 플레이어(`PlayerEntity`) = 흰색.
- 매 틱(또는 프레임, 계획 단계에서 판단) 엔티티 목록을 다시 훑어 점 위치를 갱신 — 위치 갱신은 개수 세기(CPS류)가 아니라 좌표 스냅샷이라 정확한 폴링 주기가 CPS만큼 민감하지 않다.

## 데이터 흐름

`TerrainMinimap`은 B0의 `FeatureRegistry`/`ModListScreen`에 `Category.WORLD`로 등록된다. 켜짐 상태는 기존 `ModConfig.enabled` 맵, 위치·크기는 기존 `ModConfig.positions` 맵(다른 `PositionedHudFeature`와 동일 방식) — 새 설정 필드가 필요 없다. 청크 텍스처 캐시와 반경 계산은 순수하게 이 기능 내부 상태이고 `ModConfig`엔 저장하지 않는다(재시작하면 다시 채움, 저장할 이유 없음).

차원이 바뀌면(오버월드↔네더↔엔드) 같은 청크 좌표라도 완전히 다른 지형이므로, 청크 텍스처 캐시를 전부 버리고 새로 채운다. 네더는 천장이 지형처럼 잡혀 어색하게 보일 수 있는데 특수 처리는 안 한다(알려진 제약).

## 오류 처리

- `client.player == null`(월드 진입 전/이탈 후) — 그 프레임/틱은 아무 것도 안 하고 조용히 스킵.
- 청크가 로드 해제되면(플레이어가 멀리 이동) 해당 캐시 텍스처는 그냥 버려둔다 — 다시 그 근처로 오면 새로 채워짐.
- 기능이 꺼지면 데이터 수집·렌더링을 즉시 멈춘다(`CachedConfig` 자가확인).

## 테스트

- 순수 로직 유닛 테스트 대상: 반경 안에 드는 칸 판정(플레이어 좌표+칸 좌표→포함 여부, 좌표 수학이라 Minecraft 클래스 의존 없음), 엔티티 타입 분류→색상 매핑 함수, 플레이어 위치+반경으로 필요한 청크 좌표 목록 계산.
- 실제 지형 색상 추출, 청크 텍스처 생성, 원형 마스크 렌더링, 엔티티 실시간 갱신은 Minecraft 렌더링 파이프라인에 직접 묶여 유닛 테스트 불가 — 실기기 수동 검증 대상(B0~B3와 같은 이유).
- 실기기 검증 항목: M키로 켜고 꺼짐 / 지형 색이 실제 주변 지형과 맞아 보이는지 / 원형으로 잘려 보이는지(모서리가 사각형으로 삐져나오지 않는지) / 이동하면서 새 청크가 자연스럽게 채워지는지(끊김 없이) / 엔티티 점 색상이 맞는지 / 차원 이동(네더 포털 등) 후 캐시가 제대로 갱신되는지 / 성능 저하(FPS 하락) 없는지 / HUD 편집기에서 드래그·리사이즈가 다른 요소와 똑같이 동작하는지.

## 검증 상태

이 스펙의 렌더링·API 관련 서술(`World.getTopY`류, `BlockState.getMapColor`류, `Monster` 인터페이스, 원형 마스크의 정확한 GL 기법, M키 충돌 여부)은 브레인스토밍 단계에서 개념적으로만 검토했고 **아직 실제 jar를 `javap`로 뜯어 확인하지 않았다** — B0~B3에서 반복 확인된 이 프로젝트의 원칙("API 이름이 그럴듯해도 바이트코드로 직접 확인하기 전엔 안 믿는다")에 따라, 계획 작성 단계에서 전부 검증하고 안 맞는 부분은 이 스펙을 갱신한다.

## 전역 제약 (B0~B3에서 이어짐, 계속 유효)

- Loom/Yarn/Loader/Fabric API 버전 번호 하드코딩 금지.
- **Mixin은 원칙적으로 금지**, B3에서 생긴 조건부 예외 원칙(공개 API로 정말 안 된다는 근거 + 사용자 명시적 승인 + 최소 범위)만 유효. 현재 설계는 지형 색상·원형 마스크 모두 공개 렌더링 API로 가능할 것으로 보이며, 계획 단계 검증에서 실제로 막히는 지점이 나오면 그때 이 원칙에 따라 다시 논의한다.
- 토글/설정 변경은 즉시 반영.
- 알 수 없는 설정 id는 무시.
- vanilla 키를 폴링할 땐 `wasPressed()`가 아니라 `isPressed()`+직접 edge 감지.
- 매 프레임/매 틱 무거운 작업 금지 — 청크 텍스처는 틱당 1개로 예산을 둔다(B1 성능 HUD 교훈).
