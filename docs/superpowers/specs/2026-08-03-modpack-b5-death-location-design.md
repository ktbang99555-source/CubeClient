# Sub-project B5: 죽은 위치 표시 — 설계

## 목표

플레이어가 죽으면 그 자리를 기억해뒀다가, (1) 실제 3D 월드 공간에 반투명 수직 빔으로, (2) B4의 원형 미니맵 위에 점으로 동시에 표시한다. 사용자가 직접 "전체 삭제" 하기 전까진 계속 남아있고, 여러 번 죽으면 전부 동시에 표시된다. 죽은 위치는 월드/서버별로 구분해서 저장한다 — 다른 월드에 가면 그 월드의 죽은 위치만 보인다.

## 범위 밖 (B5에서 안 하는 것)

- 좌표·거리 텍스트 HUD 표시 — 이번엔 시각적 마커(빔+점)만. 나중에 원하면 별도로 추가.
- 다른 차원/월드에 있는 죽은 위치를 향한 화살표 안내 — 그 차원/월드에 실제로 가야만 보임.
- 개별 삭제(목록에서 하나씩 지우기) — "전체 삭제" 버튼 하나만 제공.
- 죽은 위치 개수 제한이나 자동 정리 — 사용자가 직접 지우기 전까진 몇 개든 계속 쌓인다(현실적으로 문제 될 정도로 많이 죽는 경우는 범위 밖으로 둠).

## 아키텍처

### `DeathLocationStore`

```
Minecraft 객체에 의존하지 않는 순수 데이터 계층 (World가 아니라 "월드 식별자" 문자열만 다룸)
```

- 죽은 위치 목록을 파일(예: `death-locations.json`, `mod-config.json`과 별도)로 읽고 쓴다 — 기존 `ConfigStore`와 같은 패턴(Gson, 실패 시 빈 목록으로 취급).
- 항목 하나는 `(월드 식별자, 차원 RegistryKey, x, y, z)`. 월드 식별자는 싱글플레이/멀티플레이를 구분하는 문자열 키 — 정확한 획득 방법(싱글플레이 세이브 이름, 멀티플레이 서버 주소)은 계획 단계에서 실제 API를 확인하고 결정한다(아래 "검증 상태" 참고).
- `DeathLocationDisplay`(쓰기: 새 죽음 추가, 전체 삭제)와 `TerrainMinimap`(읽기: 현재 월드/차원과 일치하는 항목만 조회)이 이 저장소를 공유한다 — 두 기능이 서로 직접 의존하지 않고 데이터 계층 하나를 공유하는 구조(`CachedConfig`를 여러 기능이 공유하는 것과 같은 패턴).

### `DeathLocationDisplay`

```
Feature 구현, Category.WORLD, PositionedHudFeature 아님(화면 좌표 없는 기능)
```

- 매 틱 `client.player.getHealth()`를 확인해 하강 edge(직전 틱 살아있음 → 이번 틱 0 이하)를 죽음으로 판정 — `ToggleSprint`가 쓴 것과 같은 edge 검출 패턴, 리스폰 텔레포트가 일어나기 전이라 정확한 좌표를 잡을 수 있다.
- 죽음이 감지되면 현재 좌표+차원+월드 식별자를 `DeathLocationStore`에 추가.
- 3D 빔 렌더링을 직접 담당(`WorldRenderEvents` 훅) — 현재 월드/차원과 일치하는 저장소 항목마다 반투명 수직 기둥을 그린다.
- 모드 목록 화면의 "죽은 위치 전체 삭제" 버튼이 이 기능(정확히는 `DeathLocationStore`)을 호출.

### `TerrainMinimap` 확장

- 기존 엔티티 점(`cachedDots`)과 별개로, `DeathLocationStore`에서 현재 월드/차원과 일치하는 항목을 조회해 미니맵 위에 구분되는 색(적대/우호/플레이어 3색과 다른 4번째 마커)으로 점을 추가.
- 계산 시점은 기존과 동일하게 `onTick()`(20Hz) — "매 프레임 무거운 작업 금지" 원칙을 새로 어기지 않는다.

## 데이터 흐름

`CubeClientModClient.onInitializeClient()`에서 `DeathLocationStore` 인스턴스를 하나 만들어 `DeathLocationDisplay`와 `TerrainMinimap` 양쪽 생성자에 넘긴다(둘 다 `Category`가 다르지만 같은 저장소를 공유). `DeathLocationDisplay`는 `FeatureRegistry`에 등록되어 모드 목록 화면에서 켜고 끌 수 있다 — 꺼지면 죽음 감지와 빔 렌더링을 둘 다 멈춘다(기존 `CachedConfig` 자가확인 패턴). 미니맵 쪽 점 표시는 `TerrainMinimap` 자신의 켜짐 여부와 `DeathLocationDisplay`의 켜짐 여부 둘 다에 걸린다 — 미니맵이 꺼져 있으면 점을 그릴 화면 자체가 없고, 죽은위치 기능이 꺼져 있으면 표시할 데이터가 없는 게 맞다.

## 렌더링

- **3D 빔**: 죽은 좌표를 중심으로 반투명 빨간 수직 기둥. `WorldRenderEvents` 훅에서 매 프레임 그리며, 공개 `VertexConsumerProvider`/`MatrixStack` API만 사용한다 — 이 프로젝트가 지금까지 지켜온 "믹신 없이" 원칙을 그대로 지킨다. 카메라 상대 좌표로 변환해서 그려야 한다(월드 절대좌표를 그대로 쓰면 원점에서 멀어질수록 오차가 커짐 — 바닐라 자신도 이 방식을 씀).
- **미니맵 점**: 엔티티 점(빨강/초록/흰색)과 확실히 구분되는 색/모양으로 죽은 위치를 표시.
- 두 렌더링 다 "현재 월드/차원과 일치하는 항목만" 그린다.

## 삭제 UI

- 모드 목록 화면에 "죽은 위치 전체 삭제" 버튼 하나 추가. 누르면 현재 월드의 죽은 위치 전부(또는 전체 월드? — 계획 단계에서 "현재 월드만" vs "전체"를 명확히 코드 주석에 남긴다. 기본은 **현재 보고 있는 월드/차원 기준이 아니라 저장소 전체**를 지우는 것으로 한다 — 사용자가 "전체 삭제"라고 요청했으므로 부분 삭제로 헷갈리게 하지 않는다).
- 개별 삭제는 범위 밖.

## 오류 처리

- `DeathLocationStore` 파일 읽기 실패 → 빈 목록으로 취급(기존 `ConfigStore` 패턴과 동일), 크래시 없음. 단, `CachedConfig`가 이미 겪었던 "일시적 읽기 실패를 빈 설정으로 착각해서 저장 시 덮어씀" 위험은 이번에도 동일하게 존재 — B1에서 미해결로 남겨둔 이슈와 같은 성격이라 이번에도 낮은 확률로 수용하고 넘어간다(고칠 거면 별도 서브프로젝트로).
- `client.player`/`client.world`가 일시적으로 null인 순간(월드 진입/이탈 과도기)은 죽음 감지·렌더링 둘 다 조용히 스킵.
- 죽는 순간 정확히 좌표를 못 잡는 예외 상황(예: 월드 언로드 도중 사망 등 극단적 케이스)은 그 죽음 기록을 그냥 건너뛴다 — 크래시보다 기록 누락이 낫다.

## 테스트

- 순수 로직 유닛 테스트 대상: 죽음 edge 검출 함수(`static boolean` 형태, `ToggleSprint.nextToggleState`와 같은 패턴), 현재 월드/차원 식별자와 일치하는 죽은 위치만 걸러내는 필터 함수.
- `DeathLocationStore`의 파일 읽기/쓰기 자체는 `ConfigStore`처럼 임시 디렉터리를 쓰는 통합 테스트로 검증 가능한지 계획 단계에서 확인(기존 `ConfigStore`에 테스트가 있는지부터 확인).
- 실제 죽음 감지(`client.player.getHealth()`), 3D 빔 렌더링, 미니맵 통합은 Minecraft 렌더링 파이프라인/객체에 직접 묶여 유닛 테스트 불가 — 실기기 수동 검증 대상.
- 실기기 검증 항목: 죽으면 그 자리에 빔이 생기는지 / 미니맵에도 점이 뜨는지 / 여러 번 죽으면 전부 동시에 보이는지 / 다른 차원·다른 월드에 가면 그쪽 것만 안 보이고(또는 그쪽 기록만 보이고) 원래 월드 걸로 안 섞이는지 / "전체 삭제" 버튼이 실제로 지우는지 / 리스폰 직후 위치가 정확한지(죽은 자리가 리스폰 위치가 아니라 진짜 죽은 자리인지).

## 검증 상태

이 스펙은 브레인스토밍 직후 작성됐고, 아래는 계획 작성 단계에서 실제 jar를 `javap`로 확인해야 하는 것들이다(이 프로젝트의 "API 추측 금지" 원칙):
- `WorldRenderEvents`의 정확한 훅 시점(`AFTER_TRANSLUCENT`/`LAST` 등 중 어느 게 반투명 빔에 적합한지)과 `VertexConsumerProvider`/`MatrixStack`으로 카메라 상대 사각기둥을 그리는 정확한 API 시퀀스 — 이 프로젝트에서 처음 시도하는 3D 월드 렌더링이라 리스크가 가장 크다.
- 싱글플레이 세이브 이름/멀티플레이 서버 주소를 얻는 정확한 API(`MinecraftClient.getServer()`, `ServerInfo` 등).
- `client.player.getHealth() <= 0`이 정확히 언제 true가 되는지, 그 시점에 `getPos()`가 아직 죽은 자리를 가리키는지(리스폰 텔레포트 전인지) 실제 확인 필요.
- `ConfigStore`에 기존 유닛 테스트가 있는지, 있다면 `DeathLocationStore`도 같은 패턴으로 테스트할 수 있는지.

## 전역 제약 (B0~B4에서 이어짐, 계속 유효)

- Loom/Yarn/Loader/Fabric API 버전 번호 하드코딩 금지.
- Mixin은 원칙적으로 금지 — 이번 3D 렌더링도 공개 `WorldRenderEvents`/`VertexConsumerProvider` API로 가능할 것으로 보이며, 계획 단계 검증에서 막히는 지점이 나오면 그때 B3의 조건부 예외 원칙에 따라 다시 논의한다.
- 토글/설정 변경은 즉시 반영.
- 알 수 없는 설정 id는 무시.
- vanilla 키를 폴링할 땐 `wasPressed()`가 아니라 `isPressed()`+직접 edge 감지(이번엔 새 키바인딩 없음, 해당 없음).
- 매 프레임/매 틱 무거운 작업 금지 — 미니맵 점 계산은 기존과 같이 틱 단위로.
